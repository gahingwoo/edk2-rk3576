# RK3576 display bring-up: one stable plan

*Audit-of-audits, 2026-08-30. Everything below was re-checked against the tree at `/home/parallels/Desktop/edk2-rk3576-new`, mainline linux-next, vendor U-Boot, and RK3576 TRM V1.2. Nothing here has been on hardware since 2026-08-04.*

---

## 1. What is actually wrong, ranked

### A1. The SEC recovery-key probe resets the AHB bus interconnect and reads uninitialised DRAM, on every boot — **fix this before measuring anything else**

`Silicon/Rockchip/RK3576/Library/PlatformLib/Rk3576.c:56` calls `SaradcReadChannel(1, &KeyAdcValue)` from `ArmPlatformInitialize()`, i.e. in SEC with the MMU off. `Silicon/Rockchip/RK3576/Library/SaradcLib/SaradcLib.c:16` is `#define SARADC_BASE 0xfec10000` — an RK3588 address. On RK3576 that is plain DRAM (DRAM = `[0x40000000, 0x140000000)`), never initialised, never mapped. `SaradcStartChannel` → `SaradcReset()` (`SaradcLib.c:53-61`) → `HAL_CRU_RstAssert(RESET_SRST_P_SARADC)`; `RockchipIpRegs.h:2852` gives `SRST_P_SARADC 190`, decoded as reg 11 / bit 14 → **`0x27200A2C` bit 14, which TRM CRU_SOFTRST_CON11 documents as `hresetn_bus_biu`** — the AHB interconnect for the BUS domain (UART0, I²C, SPI, GPIO1-4, WDT, TSADC). Mainline says the SARADC APB reset is CON13 bit 6 (`rst-rk3576.c:114`).

The file's own constructor was already neutered for exactly this reason (`SaradcLib.c:121-131`: *"Touching them in SEC hangs the SoC … SARADC is not used during SEC/PEI on this port"*) — but the one live SEC caller was left in.

Per boot this: pulses the AHB BIU reset for 10 µs; writes five words into DRAM at 0xFEC10000; polls `0xFEC10110 & BIT0` on **post-DDR-training garbage**; and if that bit happens to be set and `0xFEC10120 & 0xFFF < 100`, calls `ResetPlatformSpecificGuid(&gRockchipResetTypeMaskromGuid)` (`Rk3576.c:57-61`) — a silent reboot into USB download mode. When the bit is clear it burns `SARADC_TIMEOUT_US = 100000` iterations of `MicroSecondDelay(1)`.

**Can it explain the intermittency?** It cannot explain a 75 % failure rate by itself (the maskrom path needs roughly 1 % of DRAM-garbage patterns). But it is the only mechanism in the whole tree whose behaviour is *drawn from uninitialised DRAM on every boot*, and it perturbs the bus interconnect and DRAM contents before anything else runs. It makes every cold-boot experiment uninterpretable. Nothing else on this list should be measured until it is gone.

### A2. The DCLK_VP0 mux switch and the VP0 standby dance live in the HDMI driver, and touch VOP2 registers by read-modify-write

`Silicon/Rockchip/Library/DisplayLib/DwHdmiQpLib.c:1888-1957` (step [4]) does: `MmioRead32(0x27D00C00)` at **:1922** — unconditional, not behind `RK_VOP2_DIAG_READS`; write back `DspCtrl | BIT(31)` at :1932; `REG_CFG_DONE`; 20 ms; gate DCLK_VP0 (`CLKGATE_CON61` bit 13, verified against `clk-rk3576.c:1114-1116`); write `CLKSEL_CON147` bit 11 = 1; ungate; 2 ms; write back `DspCtrl & ~BIT(31)` at :1953; `REG_CFG_DONE`; 20 ms.

Three separate problems, all in one block:

- It is an unconditional VOP2 **read** after `Vop2Enable`, which this project has a recorded hardware result against (`project_rk3576_dump_breaks_hdmi.md`).
- It re-writes `VP_DSP_CTRL` twice from a value it read back itself, silently undoing commit f780ef7's single-computed-write discipline for any field whose read-back differs from what `Vop2Rk3576.c` computed.
- It is the only operation in our sequence with **no counterpart in the vendor build**. On the DT this U-Boot ships, the vendor takes leg 2 of `rockchip_vop2.c` — `dclk_vp0_src` from VPLL/4, `CLKSEL_CON147` bit 11 **never written at all**. There is no mux switch to get wrong, and no moment where a live clock domain is stopped and restarted.

**Can it explain the intermittency?** Yes — this is the strongest structural candidate. It is the one place the pixel-clock domain is stopped, re-sourced and restarted, and the one place a cross-module read-modify-write can produce a different committed `VP_DSP_CTRL` than the one the VOP2 driver computed. Section 2 makes it go away entirely rather than trying to fix it in place.

### A3. `CMU_CONFIG0` is written with bit positions that belong to `CMU_STATUS`, to a register the RK3576 TRM does not document

`DwHdmiQpLib.c:1789`: `DwHdmiQpRegMod(Hdmi, 0, VIDQPCLK_OFF | LINKQPCLK_OFF, CMU_CONFIG0)` (duplicated at :1858 under `RK_HDMI_WARM_RESET`, currently 0). `LINKQPCLK_OFF`/`VIDQPCLK_OFF` (`DwHdmiQpLib.h:59,60`) are `CMU_STATUS` fields in mainline (`dw-hdmi-qp.h:38-42`), in the vendor BSP header, and in vendor U-Boot's header. **No reference writes `CMU_CONFIG0` at all** — across all three the only CMU access is one *read* of `CMU_STATUS`. The upstream edk2-rk3588 file this was forked from has no CMU access; this write was invented locally.

The TRM register summary goes straight from `TIMER_BASE_STATUS0 0x0084` to `I2CM_SM_SCL_CONFIG0 0x00E0` — 0x00A0 is not documented. It is not inert territory: `RESET_MANAGER_CONFIG0` (0x0048) bits 0-4 select, at their reset value, *"Value of cmu_status.linkqpclk_off_st used"* / *"…vidqpclkclk_off_st used"* — the Reset Manager decides reset overlap across the vidqpclk/linkqpclk domains from what the CMU reports.

**Can it explain the intermittency?** Plausibly, and it is a one-line deletion. Rated below A2 only because the mechanism is inferred from the Reset Manager's field description rather than observed.

### A4. VP0's AXI and post-buffer urgency signalling is never enabled — the TRM explicitly recommends enabling it

Nothing in `Silicon/` or `Platform/` writes VOP offsets 0x014, 0x018, or 0xC08. `RK3568_VP0_COLOR_BAR_CTRL` is defined at `Vop2Regs.h:284` and referenced by no `.c` file. Vendor U-Boot programs it for RK3576 VP0 only (`rockchip_vop2.c:4988-5002`, thresholds at :7457-7463 with the comment *"RK3576 VP0 has 8 lines post linebuffer…"*); the vendor BSP does the same (`rockchip_drm_vop2.c:10241-10249`). Mainline has no urgency concept at all. **TRM Part 2 §11.6.2 says outright: "Recommend enable VP0 axi0_urgency_en and set sw_urgency_thl=4, sw_urgency_thh=6."**

**Can it explain the intermittency?** No — the registers read 0 on every boot and DXE's bus load is broadly deterministic. **It is the best candidate for the black vertical stripes**: a post-line-buffer underrun on a line-buffered scanout engine lands at similar x positions on consecutive lines, which reads as vertical black bands. Cheap, TRM-endorsed, take it.

### A5. The AVI InfoFrame diverges from the working vendor binary in three fields

`DwHdmiQpLib.c:1473-1479`: `InfBuf[4] = 0x0` (PB1), `InfBuf[5] = 0x20` (PB2), and Q is set to Full **only if** `SinkInfo->SelectableRgbRange`.

Checked against the actual references rather than the code comment:
- Vendor U-Boot `hdmi_config_AVI` (`dw_hdmi_qp.c:623-745`) builds from `drm_hdmi_avi_infoframe_from_display_mode()`, which sets `active_aspect = HDMI_ACTIVE_ASPECT_PICTURE` (`drm_edid.c:7478`) → PB1 bit4 A0 = 1 and PB2 R[3:0] = 0b1000; and derives M from the mode.
- It then calls `drm_hdmi_avi_infoframe_quant_range(..., true, is_hdmi2)` with the comment *"Ignore monitor selectable quantization, use quantization set by the user"* — Q is forced, not conditional.
- It **does** override `frame.scan_mode = HDMI_SCAN_MODE_NONE` (`dw_hdmi_qp.c:706`), so our `S = 0` genuinely matches the vendor. The comment "matches vendor" is right about S and wrong about A0/R/Q.

So the correct vendor-equivalent bytes are PB1 = `0x10`, PB2 = `0x28` (16:9), PB3 Q = Full unconditionally.

**Can it explain anything?** Deterministic. Q=Default with a non-zero VIC lets a sink decode limited-range RGB against a full-range raster — crushed blacks and clipped whites, which on a dark UEFI screen is indistinguishable from "black screen". **It does not explain the horizontal offset** (the vendor sends the same `S = 0` and does not show one), and it cannot explain the stripes.

### A6. The RK3576 CRU library's `DCLK_VOP0` / `DCLK_VOP2` clock entries are RK3588 register mappings

`RockchipIpRegs.h:4558,4561,4973,4978,4980` encode, per `CruLib.h:47-75` (`[15:0]` = CLKSEL_CON index, `[23:16]` = shift, `[31:24]` = width):

| macro | value | decodes to |
|---|---|---|
| `DCLK_VOP0_SRC_DIV` | `0x0700006F` | CON**111**, shift 0, width 7 |
| `DCLK_VOP0_SEL` | `0x02070070` | CON**112**, shift 7, width 2 |
| `DCLK_VOP2_SRC_SEL` | `0x02050070` | CON**112**, shift 5, width 2 |

On RK3576 the VP0 source is **CON145** (`0x27200544`, SEL [10:8], DIV [7:0]) and the VP0 mux is **CON147 bit 11** (TRM confirmed, and `clk-rk3576.c:1105,1114`). CON111/112 are unrelated registers. So `HAL_CRU_ClkSetFreq(DCLK_VOP2_SRC, …)` — the obvious way to implement Section 2 — would write the wrong registers while correctly programming the PLL. This is the same class of bug as the reset-ID trap (`project_rk3576_reset_id_encoding_trap.md`).

Deterministic; currently latent because `Vop2SetClk` (`Vop2Dxe.c:2271-2286`) is a no-op. It becomes load-bearing the moment we adopt the fix below, so it is listed here.

### A7. Correction to the record: the rationale written into `Vop2Enable` for commit 586af04 is factually wrong

`Vop2Dxe.c:3960-3968` states that before the mux switch VP0 ran on `dclk_vp0_src` at *"plausibly gpll undivided, roughly twice VP0's 600 MHz ceiling."* TRM CRU_CLKSEL_CON145 (`0x27200544`) reset value is **`0x00000001`**: `dclk_vp0_src_sel = 0` (gpll), `dclk_vp0_src_div = 1` → divide by 2 → **594 MHz, inside the 600 MHz ceiling**. The change 586af04 made may still be right; the reason recorded for it is not. Flagged explicitly because of `feedback_sample_size_discipline.md` — this is a conclusion that would otherwise be carried forward as established.

### Deterministic, dormant, worth fixing but explains nothing observable

- `Vop2Dxe.c:2113-2115` packs `SclCalScale2(VDisplay, VSize)` into **both** halves of `POST_SCL_FACTOR_YRGB`; all three references use `(v)<<16 | (h)`. Inert today — `OVER_SCAN` is never populated anywhere in the tree, so both halves evaluate to 0x1000.
- `Rk3588SetColorFormat` (`DwHdmiQpLib.c:1360-1432`) computes the colour word from its arguments and then discards it at :1422 with a hardcoded RGB/8bpc write; the call site at :1972 passes literals rather than `ConnectorState->BusFormat`. The value written happens to be correct for the mode we force.
- `mVop2RK3576` carries `.DscData = mDscDataRK3588, .NrDscs = 2` (`Vop2Dxe.c:375-388`) though RK3576 has no DSC; `Vop2PowerDomainOn`/`Vop2WaitPowerDomainOn` use RK3588 bindings on live RK3576 addresses (0x034 is write-mask-gated on RK3576, so the `WriteMask=FALSE` write is inert, and `SYS_STATUS0` does not carry RK3576 PD status). Unreachable on the HDMI path.
- `OVL_CTRL`'s YUV bit is indexed by CRTC inside one register and `LayerSelWinID` is a flat table (`Vop2Dxe.c:2977-2985`, `:181-261`); on RK3576 VP1's overlay block is a separate register at 0x700 and VP1's LAYER_SEL encoding maps 2→Esmart1, 3→Esmart3. Only reachable in a dual-display configuration, which is zeroed out today.
- `RK3576_ESMART0_ALPHA_MAP` is written `0xFFFFFFFF` (`Vop2Dxe.c:3709`) where both vendor stacks write `0x8000FF00`. The field is RGBA5551-only per TRM; inert with an ARGB8888 framebuffer.

### Categories that yielded nothing — negative results

- **Framebuffer coherency is not the problem.** `LcdGraphicsOutputDxe.c:1079-1084` sets `EFI_MEMORY_WC` on the allocation. The VOP is not reading a stale cached framebuffer. This was my leading independent hypothesis for "valid signal, black screen" and it is dead.
- **Stride is correct.** `LcdGraphicsOutputDxe.c:1219` gives `XVirtual = 1920` for 1080p ARGB8888, matching mainline's `DIV_ROUND_UP(pitch, 4)`. Not a stripe cause.
- **VOP timing registers are byte-identical to the vendor's worked 1080p60 example** — `HTOTAL_HS_END`, `HACT_ST_END`, `VTOTAL_VS_END`, `VACT_ST_END`, `POST_DSP_HACT_INFO`, `PRE_SCAN_HTIMING`. `bg_dly = 20` matches both references. **The horizontal offset does not originate in any VOP2 timing register**, and the HDMI controller has no horizontal-position control at all.
- **HIWORD discipline in the live HDMI path is clean.** Every RK3576 register the path read-modify-writes with `WriteMask=FALSE` was TRM-checked as plain RW.
- `CLKGATE_CON(61)` bit 13 for DCLK_VP0 and `CLKSEL_CON147` bit 11 for the VP0 mux are both correct against TRM and `clk-rk3576.c`.
- No candidate for the **vertical stripes** was found in the HDMI controller — not in the packet scheduler, FIFO config, or colour path. A4 is the only structural candidate anywhere in the stack.
- The **horizontal offset remains unexplained.** The one source-side lever left is sink-side overscan on a CE VIC, and the working vendor build sends the same `S = 0`, so that lever is not obviously different for us. Section 5 has a one-line experiment that settles source vs sink.

## 2. The stable approach: adopt (b)

**Recommendation: (b) — programme VPLL to 594 MHz, point `dclk_vp0_src` at it for 148.5 MHz, and never switch `CLKSEL_CON147`.**

The framing in the brief sets this up as "clean but unproven" versus "proven but ugly". After reading both references end-to-end, that is not the choice on the table. Three facts change it:

**First, our tree already *is* (a), and mainline's (a) is not what the brief describes.** Mainline does not keep the VP on a CRU clock — `rockchip_drm_vop2.c:1915` does `clk_set_parent(vp->dclk, vop2->pll_hdmiphy0)`, then `:1941 clk_set_rate(vp->dclk, clock)` which propagates through `CLK_SET_RATE_PARENT` into `rk_hdptx_phy_clk_set_rate()` and locks the PHY ROPLL, then post_config, then cfg_done, then `VP_DSP_CTRL` with STANDBY cleared as its final register write (`:1946`). The bridge powers the PHY lanes on afterwards. Our tree does exactly this, only with the last three operations relocated into `DwHdmiQpLib` step [4]. So "adopt (a)" means "keep what we have", and what we have has the A2 defects baked into the relocation.

**Second, (b) is inside mainline's own supported envelope.** `rockchip_drm_vop2.c:1899-1900`: *"Switch to HDMI PHY PLL as DCLK source for display modes up to 4K@60Hz, **if available, otherwise keep using the system CRU**."* Mainline treats the CRU-sourced dclk as a first-class configuration, not a degraded one. So (b) is the intersection of the two references: both endorse it; only mainline endorses the PHY-sourced dclk. Adopting (b) does not put us outside either reference — it puts us inside both.

**Third, (b) is what actually deletes the risk, rather than relocating it.** Under (b), `CLKSEL_CON147` is never written, DCLK_VP0 is never gated and ungated, VP0 is never taken out of and back into standby, and `DwHdmiQpLib` never touches a VOP2 register. `DwHdmiQpLib.c:1888-1957` deletes as a block, including the unconditional `MmioRead32(0x27D00C00)` at :1922 and the two cross-module `VP_DSP_CTRL` writes. `Vop2Dxe` regains sole ownership of the VP: the dclk is programmed and locked before `Vop2Init`, STANDBY is cleared exactly once at the end of `Vop2Enable` as the last VP write, and the PHY becomes a pure downstream consumer. That is a genuine structural simplification, not another patch on the pile — which is what the user asked for.

The pixel clock and the TMDS character clock are then not phase-locked, only frequency-locked (VPLL/4 = 148.500000 MHz exactly, and the ROPLL is programmed for 1485000 kbps → 148.5 MHz exactly; both derive from the same 24 MHz xin, so there is no long-term ppm drift). The controller is designed for this: `TMDS_FIFO_CONFIG0` bit 0 `TMDSFIFO_INIT_ON_OVF` **resets to 1**, i.e. the TMDS FIFO self-heals on overflow by design. And it is the configuration the vendor ships and the vendor UEFI runs on.

**What it costs.** A VPLL programming path we must write: one new rate-table entry, one direct `CLKSEL_CON145` write (*not* via `HAL_CRU_ClkSetFreq(DCLK_VOP2_SRC, …)` — see A6), and a PLL lock wait. It gives up the theoretical benefit of a pixel clock sourced from the same PLL as the link, which matters for modes where the PHY's fractional divider can hit a rate the CRU cannot; for 1080p60 and every mode with a rate that divides evenly into ≥594 MHz it does not. If a future mode needs the PHY PLL, the mux switch can come back — but then it must live in `Vop2Init` before standby is cleared, as mainline has it, not in the HDMI driver.

**What would falsify the choice.** If (b) is implemented correctly and 8+ cold boots still show roughly 2/8, the dclk source is not the differentiator and the remaining suspects are the PHY lane/TX path and the DDR/AXI side; at that point the mux-switch hypothesis (A2) is dead and should be recorded as dead. Conversely if (b) gives 8/8, do **not** conclude the mux switch was the cause — the same change also removes the VOP2 read-back and the two cross-module `VP_DSP_CTRL` writes. Section 5 splits those.

## 3. The ordered fix list

### (i) Required for the chosen stable approach

**1. Add the 594 MHz PLL rate.** `Silicon/Rockchip/RK3576/Library/Rk3576CruLib/Rk3576CruLib.c:45-57`, in `PLL_TABLE`:
`RK3588_PLL_RATE(594000000, 2, 198, 2, 0)` — p=2, m=198, s=2, k=0. Matches vendor `clk_rk3576.c:43` exactly.

**2. Implement `Vop2SetClk` for RK3576, writing the CRU directly.** `Vop2Dxe.c:2271-2286`, currently a no-op returning `EFI_SUCCESS`. Replace with, for `CrtcId == 0`:
- `Div = ROUND_UP(594000000, Rate)`; if `Div & 1` then `Div++` (the vendor's even-divisor rule, `clk_rk3576.c:1170-1240`).
- `HAL_CRU_ClkSetFreq(PLL_V0PLL, Div * Rate)` — the `V0PLL` `PLL_SETUP` at `Rk3576CruLib.c:138-149` is correct for RK3576: con at CRU+0x160, lock on CON[6] bit 15 (= 0x27200178 bit 15, the register the vendor polls), mode at `MODE_CON00` = 0x27200280 shift 4, which TRM documents as `clk_vpll_mode` [5:4]. Verified.
- Then `MmioWrite32(0x27200544, 0x07FF0000 | (2 << 8) | (Div - 1))` — SEL[10:8] = 2 (vpll), DIV[7:0] = Div-1, hiword mask 0x07FF.
- For 1080p60: `Div = 4`, VPLL = 594 MHz, `CLKSEL_CON145` ← **`0x07FF0203`**.
- **Do not** route this through `HAL_CRU_ClkSetFreq(DCLK_VOP2_SRC, …)` (A6).

The call site already exists and is in the right place: `Vop2Dxe.c:3197`, inside `Vop2Init`, before standby is cleared — the same position as the vendor's step 37.

**3. Delete `DwHdmiQpLib.c:1888-1957` in full** (step [4] and its `HDMI_DUMP_REG` lines). This removes the VOP2 read at :1922, the two `VP_DSP_CTRL` writes at :1932/:1953, both `REG_CFG_DONE` commits, the DCLK_VP0 gate/ungate, and the `CLKSEL_CON147` write. Keep step [4c/4d] (`VO0_GRF_SOC_CON1` TMDS mode, :1959-1969) — that is a GRF write with a real justification.

**4. Restore the STANDBY clear to `Vop2Enable`** as the last VP register write before `REG_CFG_DONE`, matching mainline's `set_rate → post_config → cfg_done → VP_DSP_CTRL` order. Fold it into the deferred single-write `VP_DSP_CTRL` computation in `Vop2Rk3576.c` rather than adding a read-modify-write. Replace the comment block at `Vop2Dxe.c:3950-3980` — it documents an ordering that will no longer exist, and its factual claim about the reset clock rate is wrong (A7).

**5. Leave `HdptxRopllCmnConfig` where it is** (step [3], `DwHdmiQpLib.c:1873`). It now feeds only the TMDS link. `HdptxRopllTmdsModeConfig` at :2097 does lane registers plus `HdptxPostEnableLane` and does **not** re-run the CMN config, so there is no PLL teardown after the VP is live — verified at `PhyRockchipSamsungHdptxHdmi.c:1546-1648`.

### (iii) Deferred, with why

- **FRC 2.0 dither** (`0xCA0/0xCA4/0xCA8` + `DITHER_DOWN_EN`/`SEL=FRC`). The two references genuinely disagree, this project has a recorded hardware regression from touching the neighbouring `PRE_DITHER_DOWN_EN` (`project_rk3576_dspctrl_predither.md`), and with an ARGB8888 source expanded to 10 bits and truncated back to 8 there is no truncation error to dither. It cannot produce a black screen or vertical stripes. Defer until a flat mid-grey capture-card A/B is possible; do it alone.
- **`SYS_PORT_CTRL_IMD.dsp_vs_t_sel` = 0.** Both vendor stacks write it, mainline never does and drives RK3576 HDMI fine, so the reset value 1 is a proven-good operating condition. Alignment-with-the-known-good-binary item, not a lead. Deterministic.
- **Per-VP `OVL_CTRL` and per-VP `LayerSelWinID`.** Real, TRM-confirmed, and unreachable: with HDMI only, disabled VPs get `LayerSel = 0x0000FFFF` and `YUVOverlay` is 0. Fix before any dual-display work.
- **`.DscData`/`.NrDscs` and the RK3588 PD bindings.** Dormant; `Vop2PowerDomainOn` has two call sites and neither is on the HDMI path. Fix before any MIPI/eDP/DP bring-up.
- **`POST_SCL_CTRL` masked write** (preserving `post_vsd_dly_en`). Mainline clears the bit too and works; `post_ver_sd_en` is 0 in our configuration so there is no vertical scale-down for the bit to delay.
- **Alpha map `0x8000FF00`.** Inert for ARGB8888. Fix the *comments* at `Vop2Dxe.c:3696-3708` and `Vop2Regs.h:243-252` now — they attribute a value to "the vendor" without saying it came from binary disassembly, not from either vendor source.
- **Video-interface FIFO clear.** Under (b) the IPI clock is never stopped, so the premise disappears. Do not add it.

## 4. How to verify each fix at the desk

**Fully verifiable without hardware:**

- **Fix 1 (594 MHz entry).** Arithmetic against the table's own existing entry: `f = 24 MHz × m / (p × 2^s)`. The 1188 MHz row is `(2, 198, 1)` → 24×198/(2×2) = 1188 ✓, so `(2, 198, 2)` → 24×198/(2×4) = **594** ✓. Cross-checks against vendor `clk_rk3576.c:43` byte for byte.
- **Fix 2 (CLKSEL_CON145 write).** Three independent confirmations: TRM CRU_CLKSEL_CON145 at 0x0544 documents SEL[10:8] with `3'b010 = clk_vpll_mux` and DIV[7:0]; mainline `clk-rk3576.c:1105-1107` gives CON(145), mux at 8 width 3, div at 0 width 8; vendor `clk_rk3576.c:1170-1240` computes the same even-divisor. Compute the literal — `0x07FF0203` — and confirm it in the built binary. The V0PLL `PLL_SETUP` is confirmed against TRM CRU_MODE_CON00 (`clk_vpll_mode` at [5:4], our `modeShift = 4`) and against the vendor's lock poll address 0x27200178 bit 15.
- **Fix 2, A6 trap.** Decode `DCLK_VOP2_SRC_SEL = 0x02050070` with `CruLib.h:47-75` → CON112. Compare with TRM/mainline CON145/147. Pure arithmetic; no hardware needed. Then `grep` the built `Vop2Dxe.efi` / map file to confirm `0x27200544` appears and `0x270004B*`/`0x27200*4C0` do not.
- **Fix 3/4 (deletion and relocation).** `grep -n "MmioRead32 (0x27D0" Silicon/Rockchip/Library/DisplayLib/DwHdmiQpLib.c` must return **zero hits**, and `grep -rn "0x27D0" DwHdmiQpLib.c` must return only `HDMI_DUMP_VOP2_REG` lines behind `RK_VOP2_DIAG_READS`. `grep -n "0x054C\|CLKSEL_CON147"` must return zero. That is a mechanical, complete check.
- **Fix 6 (SARADC).** `grep -rn "SaradcReadChannel" Silicon Platform` must return only the definition. Additionally, objdump the SEC/PeilessSec image and confirm the immediate `0xFEC10000` no longer appears — this is a genuine disassembly-level check on the resulting binary.
- **Fix 7 (CMU_CONFIG0).** `grep -n "CMU_CONFIG0"` returns zero write sites. Cross-referenced against three headers that all place those bits in `CMU_STATUS`, and against a TRM register summary that has no 0x00A0 entry.
- **Fix 8 (urgency).** Register values are stated verbatim in TRM §11.6.2 as a recommendation, and independently in two vendor sources with identical thresholds. Compute the final `0xC08` word (`0x00640100`) and compare against the vendor's `vop2_mask_write` sequence field by field.
- **Fix 9 (AVI).** Compute all 17 bytes and the checksum by hand for 1080p60 RGB, then compute what `drm_hdmi_avi_infoframe_from_display_mode` + `quant_range` + the vendor's `scan_mode = NONE` override produce for the same mode, and diff. Byte-exact desk comparison, no hardware.
- **Fixes 10, 11, 14, 15, 16.** Pure register/arithmetic corrections, each with two or more references agreeing (mainline + vendor, plus TRM for bit positions). The SD clock one is arithmetically checkable end to end: 1188 MHz ÷ 13 = 91.4 MHz vs the intended 50 MHz, and the intended write mask `0x7F800000` never touches bits 6:0 (gmac0 PTP).
- **Fix 13 (PCIe LTSSM).** Verifiable against the tree's own boot log: `cm5io-boot.log:665-669` shows `LTSSM_STATUS=0x00030005` accepted as link-up, then `0x00000003` one second later and `VID:DID = 0xFFFFFFFF`. State 0x05 is not L0 (0x11). The corrected predicate is in vendor `pcie_dw_rockchip.c:637-640`.

**Cannot be verified without hardware:**

- **That (b) actually fixes the intermittency.** Nothing at the desk distinguishes a locked VPLL from a locked PHY PLL as VP0's source. This is the whole point of the board session.
- **That the urgency thresholds cure the vertical stripes.** The failure mode is an analogue-timing property of the DDR path; only a frame grab shows it.
- **That the AVI Q=Full change changes what the sink displays.** Sink-dependent by definition.
- **VPLL lock time.** The vendor's lock wait is an unbounded busy loop; ours will have a timeout. Whether 594 MHz locks within it on cold silicon is a hardware fact. Instrument it: log the iteration count, do not just log success.
- **Whether the horizontal offset is source-side or sink-side.** See Section 5.

## 5. What to measure on the board, once

Base rate is ~25 %. **Nothing below 8 cold power cycles is interpretable, and 8 is the minimum for a yes/no, not for a rate.** Distinguishing 25 % from 60 % needs ~20. Instruments per `reference_cm5io_measurement_rig.md`: raw serial capture (not through a terminal that interprets ANSI), and capture-card frame grabs with a mechanical pixel verdict — never an eyeball judgement.

**Build A — de-noise only.** Fixes 6 and 7 (SARADC probe deleted, CMU_CONFIG0 write deleted). Nothing else. 8 cold boots.
- Same ~2/8 → neither was the differentiator; both are still correct to have removed, and every later result is now trustworthy. This is the control.
- Materially better → say which of the two, then split them. Do not attribute to both.
- **This build must run first regardless of impatience.** Without it, A1 injects DRAM-garbage-dependent behaviour into every subsequent boot and no later number means anything.

**Build B — the stable approach.** Build A plus fixes 1-5. 8 cold boots minimum, 16 if the first 8 are clean.
- 8/8 picture → (b) is adopted; then, and only then, run **Build B′** which restores *only* the `MmioRead32(0x27D00C00)` read-back (not the mux switch) for 8 boots, to separate "the mux switch was the cause" from "the VOP2 read-back was the cause". These are two different fixes bundled in one change and the project has already been burned by attributing a bundle to one member.
- Still ~2/8 → the dclk source is not the differentiator. Record that as settled and move to the PHY lane/TX path and the DDR/AXI side. Do not iterate on clocking.

**Build C — stripes.** Build B plus fix 8 (urgency). 4 boots is enough because the stripes are deterministic; what you need is a capture-card grab of a known flat test pattern, before and after, with a column-histogram verdict rather than a visual one.
- Stripes gone → the post line buffer was underrunning; that also raises the prior that DDR arbitration matters here and is worth carrying into any residual intermittency.
- Stripes unchanged → underrun is ruled out and the stripes need a different theory. Say so explicitly.

**Build D — the horizontal offset, source vs sink.** One boot, one change: send `VIC = 0` in the AVI InfoFrame with the timing otherwise identical (`DwHdmiQpLib.c:1483`).
- Offset disappears → it is sink-side overscan on a CE format, and the fix is signalling (and possibly nothing at all — the sink is doing what the spec lets it do). This costs one line and settles a question that has been open for weeks.
- Offset unchanged → it is source-side, and since every VOP2 timing register is byte-identical to the vendor's worked example, the next place to look is the HDMI Frame Composer's measured-timing path, not the VOP.

**Instrument every build the same way.** Log the VPLL lock iteration count, the computed `CLKSEL_CON145` word, and the final `VP_DSP_CTRL` word that `Vop2Rk3576.c` computed — as *values written*, never as read-backs. The cross-check added in commit f780ef7 has still never been read on hardware; Build B is the run that reads it.

## 6. Non-display, prioritised

1. **SARADC in SEC** — `Rk3576.c:56`. Critical. AHB BIU reset on the wrong register, DRAM corruption, a ~1 %/boot silent reboot into maskrom, and 100 ms of dead time. Blocks all display measurement. Fix first.
2. **PCIe declares link-up out of L0** — `Rk3576PciHostBridgeLib/PciHostBridgeInit.c:355`. The `SMLH_LTSSM_STATE_*` macros it defines at :45-47 are never used. Restore the state == 0x11 check, and re-test link-up after the 1 s settle at :843 instead of falling through to a config read on a collapsed link. Proven wrong by the tree's own log.
3. **USB2 PHY resets hit reserved read-only bits** — `Platform/ArmSoM/CM5IO/.../RockchipPlatformLib.c:414-416, 430-432` and the ROCK4D equivalent at :483-485, :517-519. `CRU_SOFTRST_CON(28)` bits 0/1 are RO reserved on RK3576; the real resets are PMU1CRU `SOFTRST_CON01` bits 7/8 (`0x27220A04`, assert `0x01800180`, deassert `0x01800000`). The tuning writes are never latched by a reset, so the PHY digital block keeps whatever SPL left. Textbook instance of the reset-ID trap.
4. **SD/eMMC clocks** — `RkSdmmcPlatformLib.c:44-94` and `DwcSdhciPlatformLib.c:35-70`. Parent rates are RK3588's fictional 350/400 MHz where the real parents are gpll 1188 / cpll 1000 / xin 24; the SD mux and divider are additionally written at RK3588's bit positions (14:13/12:7 required, 15:14/13:8 written), leaving the divider LSB outside the write mask. Every SD clock lands ~1.76× high — identification near 700 kHz against a 400 kHz limit; eMMC at 148.5 MHz where 52 was intended. Deterministic, and it explains any flaky card enumeration.
5. **GMAC has no clocks at all** — `GmacPlatformDxe.c:414-450` writes no CRU register anywhere. `GmacIomux` routes GPIO3_PA4 as `ethm0_clk0_25m_out` but nothing programs the 25 MHz output behind it, no MAC gate is ungated, no MAC reset is deasserted. On CM5-IO the PHY is a crystal-less YT8531C that *needs* the SoC 25 MHz (`project_cm5io_gmac_phy_fix.md`), so this is the blocking bug for CM5-IO Ethernet specifically.
6. Everything else in the non-display sweep is below the noise floor next to these five.
