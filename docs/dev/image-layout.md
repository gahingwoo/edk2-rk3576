# Image layout

English | [简体中文](image-layout.zh-CN.md)

The tables on this page are generated by `scripts/gen-docs` from
`scripts/package.sh`, `Silicon/Rockchip/RK3576/RK3576.fdf` and the FIT that
`scripts/lib/gen_fit_its.py` and mkimage build; CI fails when they drift.

## ROCK 4D: 16 MB SPI NOR

<!-- generated:layout-spi -->

| Offset | Content |
|---|---|
| `0x000000` | GPT (`binaries/rk3576_spi_nor_gpt.img`) |
| `0x008000` | idblock: DDR init + U-Boot SPL |
| `0x060000` | FIT: BL31, EDK2, DTB, up to `0xFC0000` |
| `0xFC0000` | UEFI variable store, 64 KB |
| `0xFD0000` | FTW working block, 64 KB |
| `0xFE0000` | FTW spare block, 64 KB |

<!-- /generated -->

The three NV regions ship erased (all `0xFF`). Zeros there read as a corrupt
store rather than an empty one, and variables never initialise. On SPI NOR
the variable driver reads and writes the flash itself.

## CM5-IO and TaishanPi 3M: SD card or eMMC, 32 MB image

<!-- generated:layout-mmc -->

| Sector | Byte offset | Content |
|---|---|---|
| 64 | `0x008000` | idblock: DDR init + U-Boot SPL |
| 16384 | `0x800000` | FIT: BL31, EDK2, DTB and the UEFI variable store |
| 43648 | `0x1550000` | inside the FIT, its last image `nvdata`: the UEFI variable store, 192 KB (store, FTW working, FTW spare), erased (all `0xFF`) |

<!-- /generated -->

On SD and eMMC the variable store travels inside the FIT as its last image,
`nvdata`. The SPL loads it to `PcdFlashNvStorageVariableBase64`
(<!-- generated:nvdata-load -->0x415C0000<!-- /generated -->) on every boot, and
RkFvbDxe writes changes back to the same bytes of the card. That is the only
way a saved variable gets back into memory on these media. `package.sh`
takes the address and size from `RK3576.fdf`, finds where mkimage put
`nvdata`, and checks that those bytes of the image are all `0xFF`.

A write that keeps the settings therefore stops at the `nvdata` sector
([flashing](../flash.md#updating-the-firmware-and-keeping-everything-else)).
The web flasher reads the FIT in the image and refuses that write if
`nvdata` is not where it expects it.

`<Board>-emmc-edk2-<ver>.img` is the same bytes with a protective MBR and a
primary GPT in front:

<!-- generated:layout-emmc-gpt -->

| Sector | Content |
|---|---|
| 0 to 33 | protective MBR and primary GPT |
| 64 to 131071 | p1 `firmware` (64 MiB, no file system, type `8DA63339-0007-60C0-C436-083AC8230908`) |
| 131072 to the end | p2 `data`, unformatted, the rest of the eMMC |

<!-- /generated -->

The image stops at 32 MiB, so the backup GPT is missing until `sgdisk -e`
is run on the board. `<Board>-emmc.sfdisk` is the same table on its own.

## FIT contents

<!-- generated:fit-contents -->

| Image | Load address | Size | What |
|---|---|---|---|
| `atf-1` | `0x3fe70000` | 8 KB | BL31 segment: PMUSRAM |
| `atf-2` | `0x40040000` | 116 KB | BL31 segment: main code + entry |
| `atf-3` | `0x4005d000` | 7 KB | BL31 segment: coherent data |
| `fdt` | none | 182 KB | the DTB the SPL uses |
| `edk2` | `0x40800000` | 13312 KB | EDK2 as BL33; must match TF-A's `BL33_BASE` |
| `nvdata` | `0x415c0000` | 192 KB | UEFI variable store (SD and eMMC images only) |

<!-- /generated -->

RK3576's DRAM starts at `0x40000000`. The FIT is built with external data
(`mkimage -E -B 0x1000`): a 4 KB header followed by the payloads.

## Boot flow

```
BootROM
  -> idblock (DDR init, then SPL)
       -> SPL loads the FIT
            -> BL31 at 0x40040000, EL3
            -> EDK2 at 0x40800000, EL2 (BL33)
                 -> UEFI front page and boot manager
```
